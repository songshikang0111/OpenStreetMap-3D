# 与原版的第三轮视觉差异审计

审计日期：2026-10-30。审计基线：本项目 **v0.3 / `f3a483e`**。本文件由独立对照子代理完成，供本轮实现和后续需求排序使用；**不是 v0.4 完工评分**。

目前最值得改的已不是“多画一些窗户”，而是三个更大的视觉关系：白、网点与实黑的面积分配；建筑与街道之间的功能关系；树冠从整体明暗到细叶轮廓的层次。它们都是可在不同 OSM 地块复用的引擎能力。

## 比较边界

- 逐张查看了原版 2026-10-29 保存的俯瞰、低空、平视、路口、彩色和远景截图，以及本地 v0.3 对应类别截图。下面链接均为项目内原始证据，没有为“更像”而重绘图片。
- 原版是国贸中心 39.9095,116.4605，近区 1 km、远景 2 km；本地约 2.0 × 1.8 km。相机、太阳、数据快照和细节区都未精确配准。因此可以比较视觉机制，不能据像素差异断言楼位、树数、透视或阴影大小错误。
- 本次没有新增原版浏览器截图。2026-10-30 重新浏览了[作者说明](https://oyasumi-gamedev.com/tools/rokehan/)，核实其公开机制；截图观察仍明确限定于上述存档版本。
- **观察**指图上直接可见；**代码确认**只指我们自己的 v0.3 代码；**实现建议**是独立设计，并不声称原版使用同一算法。此前原版客户端研究的定位见[研究记录](research-evidence.md)，本次没有读取或复制原版程序。

## 最重要的发现

### 1. 网点的覆盖范围，比网点画得多细更影响漫画感

**观察：**原版街道与路口图中，大面积地面保留白色；树影和局部暗材质承担主要网点与实黑。本地 v0.3 街道中的路面、人行道以及不少墙面都铺有相近频率的网点，空间虽然可读，但整幅画的“灰底”较重。这个差异在两组平视图中重复出现，不只是俯瞰画幅不同造成的。

证据：[原版街道](original/04-street-eye-ink.jpg)、[原版路口](original/07-crossing-ink.jpg)；[本地街道](before/03-street-ink.png)、[本地路口](before/11-crossing.png)。

**代码确认：**v0.3 已把光照从玻璃等固有色中分离，但光照缓冲仍将朝光方向、环境光和投影合在 RGB 中；地面只统一乘以 `0.65`，无法明确地说“无落影的亮地面留白、落影处上网点”。

**判断：**把地面所有网点直接关掉也不合适，会一起丢掉树影和建筑投影。需要独立的落影信号及按表面类别的合成规则。这一项已经交回主代理，纳入本轮。

### 2. 树冠问题不等于面数不够

**观察：**原版彩色树也能看出球簇简化；切换到漫画后，树冠却有连贯的大暗面、白色亮叶缘和细碎边缘。本地 v0.3 每簇叶团内的黑白斑点较平均，近处像许多小团块拼成的球，远处又容易变成相似的“小棒棒糖”。原版公园图还清楚区分阔冠与细长柱状树。

证据：[原版彩色树](original/05-street-eye-color.jpg)、[原版低空树](original/03-street-high-ink.jpg)、[原版路口树](original/07-crossing-ink.jpg)；[本地彩色树](before/04-street-color.png)、[本地公园远冠](before/10-roof.png)。

**推测：**原版的细叶观感很大一部分可能来自叶缘、局部轮廓和黑白块面的配合，而不只是高模。公开说明确实提供叶缘模式和树木专用画法，但仅凭这些截图不能反推出其具体噪声函数、透明裁切方式或网格数量。

**判断：**本轮解决 LOD 切换和几何预算；下一阶段应让“整冠大明暗—叶簇—细叶缘”分工，而不是继续给每个叶簇增加噪声与三角形。

### 3. 更有建筑感，往往来自规则之间的关系

**观察：**原版中实墙小窗、带窗、深色幕墙、竖向构件的占比更有区别。本地高楼往往共享相似的玻璃填充与窗格，低楼连续带窗的比例也较高；首层、标准层和顶部仍容易读成同一段网格的延伸。彩色近镜中的玻璃尤其偏平。

证据：[原版街道小窗](original/05-street-eye-color.jpg)、[原版远景建筑分组](original/10-landmark-wide-20mm.jpg)；[本地立面近镜](before/09-facade.png)、[本地街道彩色](before/04-street-color.png)、[本地屋顶](before/10-roof.png)。

**代码确认：**v0.3 普通立面的 shader 开间和实体细节采用不同的局部计算；入口选最长外墙，没有道路朝向或共墙判断；屋顶设备是 1–6 组类似的小盒子。代码说明的是通用规则的局限，不能用它证明某个现实建筑的入口一定做错。

**判断：**先统一开间、窗台和楼层，再补“临街/背街、首层/标准层/冠部、设备/屋顶形状”的条件。没有依据时，不应把所有楼随机加退台、坡顶、招牌或空调。

## 按观察尺度复查

## 八项通用引擎需求

优先级按当前样本的预计视觉收益排序，不是工期承诺。下列验收标准是拟定的工程检查，不代表已经通过。

| ID / 优先级 | 需求与生成规则 | 可复核的验收标准 | 预计收益 / 本轮状态 |
| --- | --- | --- | --- |
| V01 / P0 | **分开落影与底色，重建白—网点—实黑层次。** 地面主要接受投影和接触 AO；墙面按材质、朝光与投影组合；玻璃和叶冠保留各自处理。复用已有中性光照通道记录落影信号，避免为此盲加渲染遍次。 | 同机位开/关投影：树影与楼影消失，轮廓和玻璃仍保留；明亮无遮挡的地面有连贯白区；改太阳方向后只有合理的投影区域移动。四种画风和 PNG 导出都回归。 | **高**。主代理已纳入本轮；完成后仍需截图验证。更完整的直接光/环境光拆分不在本轮承诺内。 |
| V02 / P0 | **统一立面语法与实体细节。** 一份布局决定楼层、开间、窗格、窗台和分格；建筑级稳定变体控制墙窗比和纵横节奏。首层与冠部按用途分段；屋顶设备以后按设备组、检修净空、建筑用途组织。玻璃用连续大尺度示意反射，不随机打碎每扇窗。 | 抽查四类普通楼近镜：框、台、窗可对齐；低中高层均无窗台穿墙或漂浮；相同 ID/seed 重建一致；近远切换保留同一大节奏；OSM 外轮廓、高度不被随机修改。彩色与漫画都能分辨不同窗墙关系。 | **高**。本轮覆盖共享布局、普通立面变体与示意玻璃层次；屋顶类型库、用途化设备组仍待做。 |

## 本轮覆盖与之后顺序

本轮正在覆盖 **V01、V02 的核心部分、V03 的 LOD 部分**。审计不会因为计划存在就提前提高分数，仍由主代理在完成截图后逐项验收。

如果只能再选两个方向，优先考虑：**树冠大明暗与细叶缘的分工（V03 剩余）**、**近处阴影和接地（V05）**。中远景竖肋噪声（V04）应与它们一起做定向回归。之后再做临街语义与屋顶组织（V06、V02 剩余）；有数据和预算后才处理地形与远城（V07/V08）。

不建议以“树更多、窗更密、设备更多”作为进度指标。建议保留固定验证场景：四类普通立面、近树/公园树/道路远树、交口、桥下、阳面/阴面、三档观察距离，以及同一画面的彩色/线稿/漫画切换。

## 来源与核实记录

原版公开说明确认：线画由面方向、深度和对象编号提取；网点考虑物色、光向及落影；近景建筑有几何细节，远树可用预渲染替身。它还提供叶缘、树木专用画法和远景地形。以上是公开功能与机制，不等于我们已验证其每一个当前渲染分支。[作者说明与实现笔记](https://oyasumi-gamedev.com/tools/rokehan/)

本地观察依据冻结在 `docs/evidence-v03/`。代码诊断针对 `git show f3a483e:src/city.js`、`src/building-rules.js`、`src/ink-renderer.js` 与 `src/main.js`，避免和正在变化的 v0.4 工作区混淆。

本报告没有发现新的卫星影像重建证据，没有复制原项目脚本、模型或纹理，也没有执行全市数据抓取。
