## 核心结论

“OSM 挤出”只解释原项目的基础空间布局。它另外有地区建筑规则、地标专用生成器、临街立面判断、近距离真实几何、程序化街道设施和成熟的漫画合成管线。因此，一个仅把轮廓拉高、给每面墙画相同窗格的版本，看起来会明显更像方块。

未发现卫星影像参与几何或颜色恢复的证据。已查到的输入是 OSM 街区数据、OSM 远景矢量瓦片和 DEM 高程。右侧彩色俯视图本身是矢量对象绘制结果，不是卫星照片。这个结论限定于已检查的数据入口和核心生成链；不能据此证明作者制作规则时从未人工参考建筑照片。

## 1. 北京国贸有专门地标规则（已证实 B）

| 发现 | 证据锚点 | 意义 |
| --- | --- | --- |
| 中国模块 `RKCN` | 59195；注册项 64403 | 生成不止一套全球通用风格，地区模块可提供层数、屋顶、立面、地标、道路、树木规则 |
| 中国尊专门 `citic()` 生成器 | 63379 | 采用随高度收缩再扩展的圆角方形截面，分层连接构成收腰轮廓；精细和轻量模式的分段不同 |
| 央视专门 `cctv()` 生成器 | 63644 | 分开构造低层基座、两座偏移的高塔、上部连接结构；并非只把一个二维轮廓竖直挤出 |
| 名称匹配中国尊/中信大厦、央视总部 | 64145、64178；地标选择段 64190 起 | 根据已知建筑语义进入专门规则，而不是从卫星图自动识别形状 |
| 中国尊、央视候选地点 | 94285、94287 | 中国尊 39.9115,116.4602；央视 39.91382,116.45797，适合本轮截图比对 |

**限制：**确认客户端存在这些生成器，不自动意味着每个数据集、每种半径、每个远景瓦片都触发它们；必须在实际同地点截图中验证。它们仍是程序化近似，不是测绘级实景模型。

**需求推导：**优先为中国尊和央视添加独立的地标形体规则。使用我们自己的截面、参数和网格实现，并在建筑卡片说明“地标形体近似”；不要将这种结果标为 OSM 原始三维结构。轮廓改善通常比增加窗户数量更显著。

## 2. 基础楼高、分部与屋顶（已证实 A/B）

- 基础数据优先读 `height`，否则按 `building:levels` 换算；用途会影响层高，缺失时按用途、占地和地区估算。楼栋 ID 与总 seed 进入确定性随机源。公开说明也提供“重抽未知高度”。锚点 13721–13752、地区高度规则 61124 起、重抽按钮 95790。
- 读取 `min_height`、`building:min_level`，区分离地结构与附着屋顶的部件。完整轮廓、裙房和 `building:part` 有去重与保留规则，不能粗暴全部一起挤出。锚点 13487、13715–13754。
- 读取 `roof:shape`，结合地区与建筑类型决定平屋顶、坡屋顶等；中国模块独立提供 `roofGeom`。屋顶设备也有 `noRoofStuff` 之类的语义排除，避免传统屋顶或特殊地标乱长设备。锚点 13724、13778 起、61348、64415–64418。

**需求推导：**本地已具备高度/分部/庭院基础，下一步应该先修正形体语义、屋顶轮廓和设备布置约束，不应把“更复杂”误当成“更真实”。有明确 OSM 高度时不能用随机形变改变总高。

## 3. 普通建筑立面不是统一贴窗（已证实 A/B）

中国规则里可见独立的住宅塔楼、板楼、小住宅、商用/公共建筑分支。条件包括用途、楼层、总高、占地、所在地区以及是否临街。锚点 60432、60920–61020、61469。

可见的参数族包括：

- 开间、窗宽窗高、窗台、窗框、百叶；
- 阳台和栏板、封闭阳台、墙面色带、竖向分隔、转角带；
- 首层商铺、入口与招牌；
- 女儿墙、冠部退台、屋顶太阳能或设备；
- 空调外机的概率与布置条件；
- 按面判断临街、入口与共墙，避免每个立面完全相同。

这些都具有受条件约束的随机变化，而非全局无约束撒物体。可见随机源由对象 ID/seed 组合产生；相同输入应稳定复现。部分细节是在近处生成真实几何，远处退回低成本窗格和楼层线。作者说明直接确认近处凹窗、阳台几何和 LOD；通用窗格着色器在 21920–21965 附近还有远距离衰减与抗锯齿处理。

**需求推导：**本地应至少区分玻璃幕墙、住宅窗格、带状窗及低层商业四类；每类具有一致的尺度、颜色和楼层节奏。首层和顶部应该有不同设计。远景主要保留大节奏，近景补窗框、窗台、分层和门厅，避免用密集黑窗铺满全部楼面。

## 4. 树木确实包含程序补充（已证实 B）

树木生成入口 `kt()`（14823 起）有多种来源：

1. OSM `natural=tree` 点：优先读树种、树高、树冠直径。
2. 道路人行道：对满足道路等级和人行道宽度的路段，按间隔补行道树，并检查地表类别与已有真实树的距离（14897–14924）。
3. `natural=tree_row`：沿折线补树（14926 起）。
4. 公园/森林：使用带抖动的采样网格、不同密度和地表分类过滤；并非在所有绿色地块满铺树（14933–14959）。
5. 院落：满足空间条件时有额外庭院植被（14960 起）。

树种优先读取 OSM 的 species/genus/leaf_type，缺失时参考地区、纬度和场景类型；道路树有沿同一条路保持树种一致的逻辑。锚点 85660–85738。树形有树干、分枝、树冠参数和树种差异（例如 85312 起）；远处使用树的预渲染图像替身，近处使用实例化几何。替身是本身三维树的渲染结果，不是从卫星照片抠出的树。

**需求推导：**本地优先增加带路面/建筑避让的行道树，保留数据来源标识；优化树冠轮廓与上下明暗。不要只是随机增加数量。

## 5. 道路和城市设施（已证实 B）

- 查询范围包含道路、铁路、水体、地面用地、道路面、边界、桥梁、交通信号、路灯、公交站、路口点、电杆等；数据入口比仅建筑+道路中心线丰富（10204–10226）。
- 道路宽度与人行道宽度读取标签并按分类补值（11984 起）。
- 斑马线结合 crossing 折线/点构造，避免重复画标线（16521、16562）。
- 交通信号、路灯、站亭和站牌都有几何分支（16826、16966–17055）；消防栓、防撞柱还能按地区规则补充（17400 起）。
- 中国道路配置有中心线、车道线、边线、斑马线样式，设施配置有横臂信号灯、站亭和街角柱（64333–64354）。

**需求推导：**近处街景缺少路缘石、斑马线、灯杆等尺度参照，会强化“积木模型”感觉。先确保道路接缝、路口连通、标线裁切，再添加少量合理设施。设施来源不能都声称来自 OSM 实测点。

## 6. 漫画管线（已证实 A/B）

原版管线不是把彩色图转灰度后叠点：

- **线条信息分开提取：**法线、深度、物体/部件 ID 用于几何边缘；窗格等程序化内部线可写入专用通道。`HGLINE` 从 23705 起；输入/合成配置 24003 起、25056 起。
- **外形与内部线分级：**外轮廓有独立粗细；远处线宽减小和变淡；装饰、接缝、微小细节有角色区分，避免远景全糊成黑团（23760 左右、88979、25066、25091）。
- **明暗来源拆分：**固有色、面朝光方向和投射阴影分开进入网点；可单独调影与固有色的浓度。网点使用屏幕空间尺度，并为导出分辨率补偿（88975–89000）。
- **留白/网点/实黑：**暗部有可调实黑阈值，树叶和窗玻璃有专用处理；黑中白线可选。锚点 25080–25093，公开说明“マンガの背景にする”。
- **空间层次：**有 AO、天空和远景雾。AO 使用法线/深度、半分辨率缓冲和深度约束的两个方向模糊（25037–25048），并不是离线烘焙。
- **树叶特殊风格：**树冠边缘有程序噪声裁切、距离衰减、树冠明暗，不同于简单球体（21974 起、22000 起）。

**需求推导：**本地优先增加独立外轮廓/内部线、远景线条衰减、浅色留白、独立网点与实黑控制、轻量 AO 与距离雾。均匀网点铺墙和过黑窗格会让效果像滤镜，应按材质家族、阴阳面和尺度区分。

## 7. 彩色俯视图是不是卫星补充（已查机制明确，外部参考未证实）

`RKMini`（93843 起）直接使用生成场景的数据绘制 Canvas：地面/水域多边形、道路宽线、建筑轮廓和树冠圆点，外加相机朝向与定位针（93896–93908）。因此界面里看起来像地图的彩色俯视图，本质是三维生成数据的二维可视化。

公开页面的数据说明列出：自托管 OSM 加工街区包；必要时 Overpass；远景 OpenFreeMap/OpenMapTiles 矢量瓦片；地形 GSI 或 AWS Terrain Tiles。代码可定位远景矢量端点 10717，以及 OSM 查询 10204 起。检查中未发现卫星 RGB 瓦片作为重建输入、图像分割、照片纹理贴图或摄影测量模型管线。

需要避免的结论：

- 不能说“原版所有细节都是真实 OSM 记录”。很多来自规则。
- 不能说“加卫星图就能得到这种效果”。已有证据不支持它依赖卫星图。
- 不能说“程序化意味着没有人工建筑知识”。地标生成器和地区规则就是人工知识编码。
- 不能把原项目脚本可读取当作允许复制。优化实现必须独立编写。
