# 拾取元数据与上传准备

在 `434e808` 中，Worker 按网格顶点的一次遍历计算每个要素的水平边界，同时在生成拾取记录时保存最大渲染 ID。主线程据此为状态纹理计费、分配空间，并复用按材质组整理好的样式角色表。单独托管的旧版 Worker 仍可加载。缺少顶点归属的网格继续使用共享边界。空矢量要素在紧邻非空要素时也会被跳过。

逐条对照北京、京都、曼哈顿、上海及阿姆斯特丹五个示例，76 块瓦片共 81,735 条拾取记录，完整对象和原实现一致。专项回归使用交错排列的顶点归属、缺少归属的网格、稀疏 ID 和几何为空的要素。可运行 `npm run build:packages && node --test packages/map/test/worker-records.test.js`。

真实 Chrome 的独立 CPU 射线与 GPU 点击身份对照命中 100/100。用 `node scripts/benchmark-tiles/overlay-checks.mjs` 重跑，见[拾取与叠加层记录](picking.json)。

另在 Node 24.18.0 构造了只有拾取元数据的网格，用于检验顶点归属扫描。样本有 32,768 个 Float32 顶点、256 个要素，顶点 i 的水平坐标为 (i % 256, floor(i / 256))，归属于要素 i % 256，索引与子网格表为空。两版交替执行 `handleRequest`，各预热两次，再取十次解码与生成耗时的中位数，从 9.82 ms 降至 1.25 ms，全部记录逐项相同。下表给出包含真实建筑生成、GPU 和上传的浏览器结果。

根测试 395/395、工作区测试 34/34，以及生产构建、示例类型与格式检查均通过。Chrome 风格检查中，启用测试规则出现 86,207 个红色像素，关闭规则后为 0。切换过滤器后原有显示状态恢复。

## 本机同路径复测

Radeon 780M、Chrome 158、1280 × 720、DPR 1、balanced 档。两版各从冷导航开始，用同一份恩克赫伊曾城区瓦片预热后跑相同的 60 秒路径，另行记录 GPU 时间。版本、瓦片指纹与时间分布见[修改前](route-before.json)和[修改后](route-after.json)。

| 实测指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 帧数 | 3,605 | 3,595 |
| 帧间隔 p95 | 16.7 ms | 16.8 ms |
| GPU 时间 p95 | 4.51 ms | 4.52 ms |
| L1 Worker 解码与生成 p95 | 140.1 ms | 162.2 ms |
| 单帧上传峰值 | 7.2 ms | 7.3 ms |

| 空白帧、瓦片错误 | 0、0 | 0、0 |

当前五城示例中，顶点最多的内置地标网格只有一个要素。城区单圈实测没有显示整帧或上传时间改善。桌面 Worker 的 120 ms 目标和上传的 4 ms 目标仍未通过。复跑命令见 [I 设备报告](../I/report.md)，将圈数设为 1。
