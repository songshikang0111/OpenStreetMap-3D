# 07 开源发布与运营

由 WP-A（地基部分）和 WP-J（发布部分）实现。

## 1. 现状问题

| 问题 | 现状 | 影响 |
| --- | --- | --- |
| 名称 | 包名 `beijing-city-ink`，产品名"城市线境 / City Ink"，仓库名 `OpenStreetMap-3D` | 三个名字，且前两个都绑定了北京和漫画风 |
| 发布 | `private: true`，未发布到 npm | 无法安装 |
| README | 开头是一期验收摘要，主体是版本更新日志，仅中文 | 新访客看不出项目是什么 |
| 仓库体积 | `docs` 约 231 MB（其中一期证据 128 MB），`.git` 约 126 MB | 克隆慢，贡献门槛高 |
| 代码可读性 | 大量单行超长语句，类型声明手写且压缩成单行 | 外部贡献者难以阅读和审查 |
| 试用 | 没有在线 demo，内置样例是合成小街区 | 无法在不安装的情况下判断价值 |
| 依赖声明 | `esbuild`、`@types/*` 位于运行时依赖 | 安装体积和供应链面偏大 |

## 2. 命名

名称由用户决定（08 的 D1）。在决定前：

- 新包统一使用 `@city-ink/*` 工作名，所有出现名称的地方集中引用一个常量或一处配置，便于以后一次性替换。
- 不注册任何 npm 作用域、域名或组织。
- WP-A 的任务 A5 准备一份候选名单（每个候选检查 npm、GitHub 上是否已被占用，并说明含义），供用户选择。

选名建议的标准：不含具体城市名和具体风格名；英文可读可拼；能体现"OSM + 3D + 城市"。

## 3. 代码规范

- 新包使用 TypeScript 严格模式，构建产出 ESM 和 `.d.ts`。
- 引入格式化和静态检查工具，行宽上限 120。
- 对一期 `src/` 做一次**纯格式化提交**：只改排版，不改任何逻辑，提交前后 `npm test` 结果必须一致，提交信息注明"仅格式化"。该提交哈希写入 `.git-blame-ignore-revs`。
- 一期 JS 模块不强制迁移 TypeScript；被抽取进新包的部分在抽取时迁移。
- 手写的单行 `.d.ts` 在对应模块迁移后由编译产物取代。

## 4. 仓库瘦身

1. 新证据不再入库大文件（已写入 [README 的 agent 须知](README.md)）。
2. 把现有 `docs/evidence*` 和 `docs/phase1-evidence` 中的截图、逐帧记录等二进制和大 JSON 移出主分支，改放到用户选定的位置（08 的 D3）。主分支保留各证据的 Markdown 结论和小摘要，并附指向新位置的链接。
3. 一期 README 中引用这些文件的链接同步更新，不留死链。
4. 是否改写 Git 历史以缩小 `.git`，必须由用户明确同意（D3）。未同意前只做第 2 步的普通提交。
5. `public/data` 中的 OSM 样本（约 39 MB）评估改为按需下载或压缩存放；保留每份数据的来源、时间和许可。

## 5. README 与文档

README 改为英文为主，另提供 `README.zh-CN.md`（主语言由 D4 确认，默认英文）。结构：

1. 一句话定位和一张动图或截图。
2. 在线 demo 链接。
3. 五分钟上手：安装、十行代码、预构建城市的地址。
4. 换成自己的城市：一条构建命令。
5. 换风格：一个样式配置的例子。
6. 叠在 MapLibre 上的例子。
7. 它是什么、不是什么（引用 00 的边界，包含中国大陆数据与合规的提示、文字标注的限制）。
8. 真实与推断的说明。
9. 贡献入口、路线图、许可与署名。

一期的版本历史移到 `docs/history.md`。

文档站内容（可先以仓库内 Markdown 形式存在）：

- 概念：瓦片、级别、语义角色、来源等级。
- 指南：上手、自建城市、样式配置、自定义风格包、叠加业务数据、MapLibre 集成、移动端 WebView 注意事项、静态托管（范围请求、压缩、跨域）。
- 参考：`createMap` 接口、样式配置规范、瓦片格式、CLI。
- 面向 agent 的接入说明：一份单文件的精简文档（`docs/llms.md`），包含最小可运行例子、全部公共类型、常见错误码及处理方式。

每个代码例子都必须有对应的可运行文件并纳入类型检查，不允许文档中存在无法运行的示例。

## 6. 在线 demo 与预构建城市

- `apps/demo` 是一个纯静态站点：城市切换、风格切换、真实性过滤开关、点击建筑显示属性、一个加标记的例子、一个 MapLibre 图层模式的页面。
- 预构建城市清单见 [03 第 9 节](03-build-pipeline.md)。
- 托管位置由用户决定（D2）。准备工作（构建脚本、部署工作流文件）可以先完成并在本地验证，但实际部署、开通任何托管服务都需要用户同意后才执行。
- 托管要求：支持范围请求（若用单文件归档）、允许跨域读取、有压缩。
- demo 页面必须显示 OSM 署名。

## 7. npm 发布

- 发布顺序：`tiles` → `generators` → `styles` → `map` → `builder`，其余包随后。
- 版本从 `0.x` 开始，明确说明 1.0 之前接口可能变化；每次变化写入 `CHANGELOG.md`。
- 依赖整理：构建工具移到开发依赖；`three` 为 peer 依赖并声明测试过的版本范围；`maplibre-gl` 为可选 peer 依赖。
- 每个包的发布内容只含构建产物、类型、README 和许可；用 `npm pack --dry-run` 检查文件清单并在 CI 中校验。
- 实际执行 `npm publish` 需要用户同意并由用户提供凭据，agent 只准备到"可以发布"的状态。

## 8. 贡献者体验

- `CONTRIBUTING.md` 重写：环境、常用命令、包结构地图、如何加一种屋顶、如何加一条 OSM 标签解析规则、如何加一个角色、测试与证据要求。
- Issue 模板：缺陷（含复现用的经纬度和瓦片编号）、数据问题（某地渲染不对）、功能建议。PR 模板含自检清单。
- 准备不少于 10 个标注为入门的 issue 草稿，优先选择"某种 OSM 标签未支持""某种屋顶形状未支持"这类边界清楚的任务。草稿放在 `docs/phase2/starter-issues.md`，由用户决定何时发到 GitHub。
- 公开路线图：`ROADMAP.md`，内容来自本计划书的里程碑和后置清单。
- 行为准则和安全问题报告方式各一份。
- CI：Linux 和 Windows 上的测试、类型检查、构建、包文件清单检查、瓦片体积与包体积预算。

## 9. 许可与署名

- 代码与配方 MIT；OSM 数据及其衍生的瓦片 ODbL。两者在 README、`DATA_LICENSE.md` 和每个瓦片集的元数据中分别说明。
- SDK 默认显示署名控件。
- 预构建城市的发布页必须注明数据时间和来源。
- 新增第三方依赖时检查许可兼容性，并在交付报告中列出。
