### E1 根包依赖整理中 esbuild 与类型包的归属（2026-11-12，WP-A）
- 问题：A7/AC108 要求根包运行时依赖不含构建工具和类型包。但一期 `src/styles/project-bundle.js` 在运行时按需 `import('esbuild')` 打包项目风格（CLI `export web` 与工作台都用到），一期包检查要求离线安装后能完成该流程；一期 `.d.ts` 引用 `three` 和 Node 类型，消费者在 `--omit=dev` 安装后仍需通过严格类型检查。
- 选择：`esbuild` 移到 `optionalDependencies`（默认安装，缺失时已有 `STYLE_BUNDLER_MISSING` 诊断）；`@types/three`、`@types/node` 同时列入 `devDependencies` 和 `peerDependencies`（npm 7+ 自动安装非可选 peer）；`typescript`、`vite`、`prettier` 只在开发依赖。`scripts/phase1-package-check.mjs` 相应改为断言 `optionalDependencies.esbuild`。
- 理由：保持一期 CLI 风格打包与消费者类型检查行为不变，同时让运行时依赖只含运行时代码。
- 影响的规格和工作包：07 第 7 节；WP-J 发布各包时按同样原则处理类型包。

### E2 水平量化网格与墨卡托对齐，int16 范围以瓦片宽度计（2026-11-12，WP-B）
- 问题：02 第 5.2 节写"分辨率 1/32 m、范围约 ±1,024 m"（固定米制），同时 AC203 要求相邻瓦片共享边界上的顶点量化后墨卡托位置完全相同。固定米制网格在不同纬度的相邻瓦片间无法对齐。
- 选择：使用全局墨卡托对齐的整数网格，每块瓦片边长 2^extentLog2 个单位（L1 默认 2^14，L0 默认 2^15），原点在瓦片中心。北纬 40° 处 L1 分辨率约 2.9 cm、范围约 ±937 m（±2 块瓦片宽）；L0 分辨率约 5.7 cm、范围约 ±1 块瓦片宽。赤道处 L1 误差上限 1.9 cm，L0 3.7 cm，均满足 5 cm。高纬度处米制范围随瓦片缩小，但以瓦片宽度计不变。超出范围的对象改用网格层 f32 编码。
- 理由：只有全局对齐的网格才能让 AC203 精确成立（测试 2,000 个随机边界点差为 0）；以瓦片宽度计的范围才是"对象可伸出瓦片多远"的真正约束。
- 影响的规格和工作包：02 第 5.2、9.6 节；WP-C 的超界检查用 `fitsInt16` 判断。

### E3 不采用额外的网格压缩与顶点差分编码；14/16 两级保持不变（2026-11-12，WP-B）
- 问题：B5 要求决定是否在 HTTP gzip 之外再做网格压缩，并核对两级缩放的选择。
- 测量（`node scripts/benchmark-tiles/codec-measure.mjs`，摘要见 `evidence/B/codec-measure.json`）：合成代表性瓦片 gzip 后为：密集低层 48 KB、极密老城 70 KB、高层 CBD 含 1.2 万三角形随机地标网格 233 KB、立交 69 KB、L0 体块 135 KB；Node 解码第 95 百分位均不超过 1 ms（零拷贝视图）。真实数据上的差分实验（曼哈顿金融区 456 栋、6,084 个顶点）：按环差分后 gzip 仅从 19,836 B 降到 18,610 B（约 6%）。
- 选择：格式 1.0 存绝对 int16 坐标、不做差分、不引入 meshopt 等网格压缩，依赖托管方的 gzip/brotli。L0/L1 维持缩放 14/16。
- 理由：解码耗时远低于预算，零拷贝是运行时的主要收益；6% 的体积收益不足以抵消额外的解码遍历和格式复杂度。CBD 样本超出中位数预算主要来自随机生成、不可压缩的地标网格，真实地标需要在 WP-C 用实际瓦片复测。
- 待复核：WP-C 用一期真实样本构建后复测体积（AC302）。若地标网格层成为主要体积来源，再评估网格压缩，并以新的主版本号引入。
- 影响的规格和工作包：02 第 5.4、6 节；WP-C、WP-I。

### E4 生成器抽取采用"一期模块单一来源 + 类型边界"，瓦片新增上下文层与地表合并（2026-11-12，WP-C）
- 问题：01 第 5 节要求把一期建模代码按"规划/生成"拆进 `builder` 与 `generators`，C10 要求不得出现两套各自演化的建筑生成逻辑；一期建筑的围护面（共墙、屋顶遮挡）是跨对象计算，单块瓦片内无法独立完成；一期道路规划每个路段输出一片路面，单块瓦片可达两万片。
- 选择：
  1. 一期 `src/` 中被复用的模块（`building-envelope`、`roofs`、`building-rules`、`facade-layout`、`generators/mesh-tools`、新抽出的 `building-mesh`，以及规划用的 `osm`、`road-surface`、`streetlife`、`landmark-registry`）保持为唯一来源，在原位置补充 `.d.ts` 作为类型边界，新包以相对路径引用。一期场景路径与瓦片路径调用同一个 `writeBuildingBody`。
  2. 建筑围护面在运行时由生成器计算；构建期在每块 L1 瓦片中写入 `buildingContext` 层：归属其他瓦片、但与本瓦片建筑包围盒接触的邻居建筑的轮廓与高度（只参与计算，不渲染）。
  3. 平坦且同类、同高程的地面碎片在每块瓦片内求并集后写为一个多面要素；坡道和路面标线保留原要素。覆盖范围不变。
  4. 规划格不得细于最粗内容级别（默认 z12 ≤ L0 的 z14）；读取范围按"道路名称组"扩大，以保证一期按路名取随机流的行道树与划分无关（03 第 4.2 节"按需扩大读取范围"）。
  5. `building` 层新增 `area` 属性（一期规则用到的占地面积，避免量化后阈值翻转）；地标为 `landmark` 网格层，顶点色存为 `color` 顶点属性。
  6. 入口雨棚选取最长墙时，长度差在 10 cm 内保持第一面墙（一期行为的微小变化），使 3 cm 量化不会把雨棚移到另一面墙。
- 理由：保证两条路径几何一致（AC306：888 栋中 886 栋包围盒差 ≤ 2 cm），并让瓦片可单独生成；一期代码不做大规模迁移（R10）。
- 影响：WP-D 的 Worker 需要打包 `src/` 中这些模块；发布 `@city-ink/generators` 前（WP-J）需把这些模块物理迁入包内或打包进产物，届时以本记录为依据。02 第 5.3 节新增 `buildingContext` 层与 `area` 属性（向后兼容的次要扩展）。

### E5 AC312 单瓦片生成耗时未达 60 ms（2026-11-12，WP-C）
- 测量：`node scripts/benchmark-tiles/generate-measure.mjs <样本目录>`，167 块 L1 样本瓦片，Node 单线程、预热后取 3 次中位数：p50 5.8 ms，p95 约 130 ms，最大约 190 ms（摘要见 `evidence/C/generate-measure.json`）。超出的全部是建筑密集瓦片（京都祇园、曼哈顿、马拉喀什，每块 600–1,300 栋），建筑占总耗时的 90% 以上，其中立面网格写入与 GC 为主。
- 已做：去掉每个三角形的对象分配、批次一次性拷贝，p95 从 237 ms 降到约 130 ms，几何不变。
- 处理方式：生成只在 Worker 中进行（04 第 5.3 节），不占主线程；06 的桌面 Worker 预算为 120 ms，移动为 500 ms，需在 WP-D/WP-I 用真实浏览器测量。后续可选：MeshWriter 改为类型化缓冲（预计再降 30–40%）、把立面装饰条改为近景细节按需生成。
- 结论：AC312 记为"未通过"，原因与处理已列出；不调整统计口径。

### E6 地图运行时内核未与一期 `createCityViewer` 合并；临时风格不复用一期 `color` 风格绑定（2026-11-12，WP-D）
- 问题：D1 要求把一期 `src/runtime` 的预算、策略、资源回收、统计、GPU 计时抽成两种模式共用的内核；D6 要求在 WP-G 之前用一期 `color` 风格绑定瓦片场景。一期运行时以"场景包分块 + 多级网格 LOD"为单位组织（`ChunkStreamer`、`budgetPlan` 按分块 LOD 计费），一期风格绑定针对整个场景组一次性安装着色器；直接复用需要先改写一期运行时，会动到 AC413 覆盖的一期测试面。
- 选择：`@city-ink/map` 先实现自己的瓦片调度与预算（三档质量取 06 第 3 节数值，`balanced` 与一期默认一致），`createCityViewer` 原样保留（AC413 全部通过）；临时风格为按语义角色的 `MeshStandardMaterial`，沿用生成器写入的一期立面配色（顶点色）。两者的合并与 `StyleSpec` 解释器分别留给后续迭代和 WP-G。
- 理由：先交付可验证的瓦片运行时（AC401–AC414 中可在本机验证的全部通过），不冒险改动一期已验收的运行时。
- 影响：WP-G 实现风格时需同时覆盖瓦片模式与场景模式；"一份内核两种模式"仍是待办，记入 WP-D 报告的未完成项。Worker 产物包含 three.js 数学部分与一期建筑代码（约 443 KB，未压缩），主包 67 KB。

### E7 观感修复：L0 与 L1 同色、桥梁附属结构编码、屋顶设备阈值（2026-11-12，WP-C 补充 C2）
- 问题：独立审查发现 (a) L0 主干道带的顶面朝下被背面剔除，远景没有道路（02 第 2 节要求 L0 有主干道平面带）；(b) L0 体块用固定浅灰，L1 用一期立面配色，交界处色差明显；(c) C4 只生成了桥面板，缺桥墩、护栏和楼梯；(d) 一期 `roofEquipment` 只看占地面积（≥ 160 m²），京都两层町屋也放了屋顶设备。
- 选择：

### E12 PBF 读取方案：自研流式解码、三遍读取；整城构建暂受全局解析限制（2026-11-13，WP-F）
- 问题：03 第 2 节要求流式两遍读取、节点坐标存放在类型化数组、读取方案由 WP-F 评估。PBF 中关系排在路径之后，第一遍读路径时还不知道哪些无标签路径是关系成员；另外现有规划阶段对整个输入做一次一期解析（`parseOSM`），再按规划格裁取，没有"要素存储 + 按格读取"。
- 选择：
  1. 不引入依赖，自写约 300 行的 PBF 解码（`packages/builder/src/ingest/pbf.ts`：逐块读文件、`node:zlib` 解压、手写 protobuf 读取，支持 dense 与普通节点、路径、关系、头部范围与复制时间戳）。理由：只需要很小的子集；现有 npm 实现多为非流式或不再维护；MIT 兼容问题不存在。
  2. 三遍读取（关系 → 路径 → 节点），而不是两遍：第一遍只解码关系，取得成员路径集合；第二遍按标签过滤或成员关系保留路径并收集节点 ID；第三遍把节点坐标填入排序的 `Float64Array`（二分查找），并收集有标签的点要素。每遍只驻留一个数据块；144 MB 的阿姆斯特丹文件单遍完整解码约 3 s（本机）。偏离"两遍"的代价是多一次顺序读文件。
  3. 过滤规则集中在 `ingest/filter.ts`，与一期 Overpass 查询一致；输出为一期 Overpass "out body geom" 形状，规划阶段不变。
  4. 规模上限按 03：输入超过 1 GB 或构建范围超过 5,000 km² 时报 `PBF_TOO_LARGE` / `BUILD_AREA_TOO_LARGE`，提示用 `osmium extract` 裁剪。
- 限制：规划仍对构建范围内的全部要素做一次一期解析，内存和耗时随范围线性甚至更快增长（实测见 WP-F 报告）；按规划格从要素存储读取（F4）、并行（AC606）、过大组诊断（F5/AC607）、单文件归档（F7/AC608）未实现。整城构建因此尚未完成。
- 影响的规格和工作包：03 第 2 节（三遍）；WP-F 剩余任务；WP-I 的首屏下载量（AC904）依赖整城产物。

### E15 按材质组合批，逐顶点角色索引（2026-11-13，AC903）
- 问题：批次按"图层:角色"划分，加入结构、装饰、场地层后 L1 瓦片最多 17 次绘制调用、L0 6 次，超过 06 的 12/4。
